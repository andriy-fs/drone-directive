# Drone Directive — Pixi rendering + bridge (PixiJS v8, miniplex)

Owns the canvas and bridges the `GameEngine` to the store. **No React imports.** May import `client/src/engine/**`, the store (vanilla `useGameStore.getState()`), and — in `GameApp` only — `@drone-directive/net`.

## Files

- `GameApp.ts` — the boundary object React mounts (via `useGameApp`). Owns the `GameEngine`, `WorldRenderer`, camera, obstacle graphic. `init()`: `app.init` → `loadGameAssets` → build layers/camera → `new GameEngine()` → `WorldRenderer(layers, engine.world)` → `wireBus()` → pointer → loop. The loop `update` = `step(dt)`; `render` = `worldRenderer.sync(selectedIds, isVisibleToPlayer, now)` — `now` is **one** `performance.now()` read per frame, shared with the order marker and the hover reticle so everything animated on screen pulses in the same phase (and keeps pulsing while paused). `isVisibleToPlayer(e)` is the fog-of-war gate: player/neutral entities are always visible; an AI robot/base is only visible once `engine.context.intel.player` (see dd-engine's `TeamIntel`) has it in `visibleRobotIds`/`knownBaseIds`.
  - **step(dt):** apply store control flags (`restartRequested`→`engine.startMatch(config)`, `menuRequested`→`engine.toMenu()`, then `clearRequests()`); `engine.setPaused`; forward `drainCommands()`→`engine.enqueueCommand`; `engine.tick(dt)`; throttled `pushSnapshot`.
  - **wireBus():** `projectileFired`→`sfx.missileShot`/`sfx.cannonShot` (by `WeaponType`), `entityDestroyed`→`sfx.explosion` + snapshot + drop a selected base that just died (`selectBase(null)`), `entitySpawned`→snapshot + `sfx.unitReady` for own-side robots, `sceneChanged`→status + rebuild/clear obstacles + snapshot, `gameOver`→status won/lost.
  - **Selection audio is *not* on the bus.** Selection is store-only state, so `init()` also calls `attachSelectionAudio(engine.world)` (disposed in `destroy()`) — the second audio adapter.
  - **pushSnapshot():** projects `world.with('base'/'robot').entities` into store `BaseSnapshot`/`RobotSnapshot` DTOs + resources from `engine.context`.
- `render/WorldRenderer.ts` — **reactive queries**, taken from `engine/ecs/queries.ts` and held archetype-typed (`Query<BaseEntity>`, `Query<ShieldedBase>`, …); `onEntityAdded`→create view, `onEntityRemoved`→destroy view; per-frame `sync(selectedIds, isVisible, now)` updates transforms/HP/selection/fog-of-war visibility. `bind<E extends Entity, V>` is generic over the archetype, which is what lets each view constructor take the kind it actually draws. **A component can be a query**: `world.with('base','position','shield')` means "bases whose energy dome is up right now", so raising and losing a dome creates and destroys `ShieldDomeView` for free — including a base reaped with its dome still standing. That only works because the engine attaches/detaches `shield` through `world.addComponent`/`removeComponent`; a plain assignment would leave this query blind. (There is **no cast** here any more: `queries.ts` hands back an already-narrowed `Query`, so `BaseView` reads `base.footprint` and `ExplosionView` reads `explosion.effect` with no `??` fallback or null re-check for something the query guaranteed. `isVisible` stays `(e: Entity) => boolean` — it is called with every kind and legitimately branches on the tag.)
- `render/ShieldDomeView.ts` — the energy dome, on **`layers.fx`** (not `units`): it has to draw over the base, over the robots under it and over the rounds crossing it, and on `units` it would sit beneath both and read as a floor decal. `fx` is above `fog`, so it gates itself with the same `isVisible(base)` every other view uses. Three marks, because three things must be legible at once: a pulsing owner-coloured ring (it is there), a depletion arc (how much is left — what makes a 1000 hp pool readable without a number), and a white snap on any frame `shield.hp` fell (it is being hit *now*). That last one is inferred from a last-value compare, deliberately: absorbed rounds are far too frequent to spawn an entity for, and anything in the world lands in `worldHash`.
- `render/{BaseView,RobotView,ProjectileView,ExplosionView}.ts` — take their **archetype** (`BaseEntity`/`RobotEntity`/`ProjectileEntity`/`ExplosionEntity`), read components (`position/heading/hp/maxHp/chassis/weaponType/owner/effect`). HP bars live here (per-frame), not React. `RobotView.update(robot, selected, visible)` / `BaseView.update(base, visible, selected)` toggle `container.visible` for fog of war — the view stays alive (not destroyed) while hidden, so it snaps back instantly once known again. Both draw a `palette.selection.ring` selection outline (circle / footprint rect); `RobotView` additionally shows a `palette.vision.spotted` highlight ring on enemy robots whenever `visible` is true (i.e. currently detected), and a `palette.blast.zone` radius ring on bomb-armed units. Only own-side views are `eventMode: 'static'` (enemy views stay pointer-transparent so right-clicks reach the stage → attack order): `RobotView` handles click-select + double-click "select all with this weapon"; `BaseView` handles double-click → `setBuildDialogOpen(true)` only — *selecting* a base is the stage handler's job in `input/pointer.ts`, because a click here bubbles anyway and would be undone by the stage's deselect. Both share `input/doubleClick.ts`'s `DOUBLE_CLICK_MS` and let single clicks bubble to the stage. **A status effect needs its own picture or it doesn't exist to the player** — the `dew` knock-out is drawn on three independent channels because a weapon that deals no damage has no explosion to borrow: a fat bolt in `ProjectileView` (`kind: 'dew'`), an `EffectKind.Emp` discharge ring in `ExplosionView` (spawned by `spawnEmpBurst`, sharing the `explosion` archetype so ageing and the view lifecycle come free), and a per-frame crackling cage + dimmed hull in `RobotView.drawStunned`. `ExplosionView` branches on `effect.kind`; absent = `Blast`, the original fireball. `ShieldBreak`/`ShieldExpire` (spawned by `spawnShieldEnd`, same borrowed archetype) are drawn as visual opposites — a shell coming apart into shards versus one ring contracting softly — because the player must know at a glance whether the dome was beaten down or simply ran out. **A base shoots, so it has to look like it does:** `BaseView` draws the built-in missile launcher over the body and rotates it by `base.heading` (written by `taskSystem`'s turret pass) — a projectile appearing out of a building with no visible source reads as a bug, the same lesson the `dew` channels above encode. **`DroneView` is owner-aware, unlike `teamTint`'s rule:** there is only *one* drone art set, where robots and bases have two, so an untinted enemy drone would look pixel-for-pixel like your own in a 1v1. The local side keeps the authored look; every other side is recoloured with `ownerColor`.
- `render/{gait,dust}.ts` + `RobotView.move()` — **how a unit looks like it is moving**, on two channels, both clocked off *ground covered* rather than the wall clock (no travel, no step — so stopping, chassis speed and a unit inching around an obstacle all fall out for free). `gait.ts` picks the cell of a chassis's 2×2 movement sheet (`robotGaitSprites` + `GAIT_STRIDE_PX` in `config/sprites.ts`); `dust.ts` is a Pixi-free `DustTrail` of world-space puffs laid down behind the drive and faded in place, drawn by `RobotView` into a `Graphics` that is the **first child of `container`, not of `body`** — `body` carries the heading and the sway, while a puff belongs to the ground it was dropped on. `RobotView`'s `GAIT_BODY`/`DUST` tables tune both per `ChassisType`. **The renderer's channels are the ones that read at 46 px**: a sheet's per-cell change is a couple of pixels with no zoom, which is why a chassis whose sheet is not drawn yet (or failed to load) still does not slide. Both use `Math.random` for jitter, which is fine here and *only* here-adjacent — never the engine's seeded `Rng`, see `terrain/hash.ts` below.

- `render/RallyView.ts` — GameApp-owned (not ECS-bound) `Graphics` in the `overlay` layer, drawing the **local side's** rally flags plus a leader line to the base that owns each. Both peers hold every base's `production.rally`, so this filter is what keeps the opponent's gathering point off screen. Redraws only when a marker moves.
- `render/terrain/` — the terrain field, `createTerrainView(terrain)` from `engine.context.terrain` (rebuilt per match on `sceneChanged: game`, on `layers.ground` so fog still hides it). **Drawn as landforms, not cells** — the old `ObstaclesView` put one sprite on every blocked cell, which gave the field a 32 px period and left every cluster a staircase of identical squares. Now: `clusters.ts` (pure, tested) flood-fills the `TerrainGrid` into single-kind 4-connected clusters and derives boundary edges + a Chebyshev distance transform; `TerrainView.ts` draws one **masked world-sized `TilingSprite` per `TerrainKind`** (texture continuous in world space → no seam inside a cluster) plus procedural form on top: stacked-offset cast shadow (mountains only), depth shading from the distance transform, and a boundary rim whose lit/dark sides are **inverted between mountain and crater** — that inversion is how the player tells apart the cover they can shoot through. Ridge decals (`terrain-peaks`) and the crater halo (`terrain-ejecta`) are optional sprites; missing art degrades pass by pass to the flat `palette.obstacle` fill.
  - **Two hard constraints, both worth keeping:** no `RenderTexture` (the app renders at `devicePixelRatio`, so a world bake is ~105 MB at dpr 2 on the large map) and **no filters** (a `BlurFilter` on a world-sized container costs fullscreen passes every frame for a layer that never changes) — softness is geometric instead.
  - `render/terrain/hash.ts` — the renderer's **only** randomness: a pure coordinate hash. Never use the engine's seeded `Rng` from `pixi/`; consuming that stream desyncs lockstep, and only on the client that drew the extra decal.
- `render/fpv/` — **the second renderer**, and the only thing under `pixi/` that is not part of the top-down view. While the local side's drone is riding a robot (`possessedRobotOf(ctx, side)` in `engine/targeting.ts`), `GameApp.syncFpv` hides `camera.view` and shows `FpvView`'s container — a wireframe of the battlefield seen from behind that hull, on a 1980s sensor monitor. **The view is *replaced*, never tilted**, and that is what the whole thing costs so little: nothing built for a square top-down grid (fog rectangles, health bars, selection rings, radius circles, the pointer hit-test) has to survive being seen at an angle, and letting go puts them all back untouched because they were never transformed. The switch is derived from the world every frame rather than latched — `droneSystem` clears `possessedId` by itself when the hull dies, and a boolean would have to enumerate release/death/game-over/menu/restart/disconnect and would strand the player in a machine that no longer exists the first time one was missed.
  - `camera.ts` (pure, tested) — **the one projection.** Builds a world→clip `mat4` from `robot.position`/`heading` plus `gameConfig.drone.fpv` (follow distance, height, pitch, fov, near). The terrain is projected on the GPU and the units on the CPU, but from the *same sixteen numbers* — never a shader-side transcription of the same formula, which would be correct only until one of the two was edited. Adds a `z` axis running **up** and leaves `x`/`y` exactly as the world has them.
  - `ground/geometry.ts` (height field pure + tested) — the relief is **read off the top view's** `findClusters`/`depthField`: a distance transform already answers "how deep inside its landform is this tile", and the two views must not derive height twice. Corner heights are the average of the four touching tiles, so the surface cannot tear. `terrainGeometry` builds one static `topology: 'line-list'` `Geometry` per match (strided grid + `clusterContours` outlines) — one buffer, one draw call, nothing rebuilt per frame.
  - `ground/shader.ts` — GLSL only, like `terrain/terrainShaders.ts`. The vertex stage needs a perspective divide, which a container `mat3` cannot express, so `uViewProj` does the camera — and then Pixi's `uProjectionMatrix * uWorldTransformMatrix * uTransformMatrix` is applied **after** it, not instead of it. **Applying it is not optional**: it used to write its own NDC, which is right only while the mesh renders to the canvas. Under a filter Pixi draws into a pooled texture rounded **up to a power of two** (980×800 → 1024×1024), binds the whole thing and compensates in those matrices; a shader emitting NDC ignores the compensation and spreads over the entire target, so the ground came out stretched and shoved up the screen while the machines standing on it — drawn through Pixi's transform — stayed put. The composition is written so the near-plane clip survives: `uViewProj` yields **pixels premultiplied by `w`** (`camera.ts` folds the viewport in for exactly this reason, so neither consumer writes it out again), Pixi's matrix is affine, so the product stays linear in clip space and `z`/`w` pass through untouched. Distance fade in the fragment stage is what keeps the far half of the map from landing as noise.
  - `fogMask.ts` — `fog.explored`/`fog.visible` as a **texel-per-tile `BufferImageSource`**, sampled per fragment. This is what lets the geometry be the *whole map* and still be static: drawing all of it would be a free survey of ground the side has never approached. Same `fog.version` redraw gate as `render/FogView.ts`.
  - `models.ts` — every machine as a segment list in local coordinates (`x` forward, `y` right, `z` up), authored against the **sprite briefs** so a player who can tell a walker from a buggy from above reads the same proportions from inside one. `CHASSIS` and `WEAPONS` are exhaustive `Record`s over `types/src/enums.ts`; `ROBOT_MODELS[chassis][weapon]` is the 3 × 8 composition, built once at module load by lifting the module onto the chassis's `deck`. **A new unit is now two jobs** — a sprite and a model — and a missing model makes that unit invisible in a hull, which is why the `Record`s (and `models.test.ts`) exist. A base is two models: `BASE_BODY` drawn square to the world and `BASE_LAUNCHER` drawn at `base.heading`, because that field is the battery's bearing, not the building's.
  - `units.ts` — rotation, projection, and the stroking, plus **heat**. Segments carry a `NodeKind` (wheel/joint/engine/barrel) and a marked segment is drawn *twice*: structure in the role colour, then the node again in `palette.fpv.heat` at its rate, thicker (colour alone cannot carry it — `self` is already near-white and anything redder collides with `foe`). **Heat needs nothing new from the simulation**: `weapon.cooldownLeft / weapon.cooldown` is "just fired", `hypot(movement.velX, velY) / movement.speed` is "driving hard". That holds for the pilot's own hull too: `droneSystem` moves a possessed hull directly and records what it drove, so no machine on this screen needs a renderer-side reading of its own.
  - `FpvView.ts` — assembles all of it. Gated by the **same** `isVisibleToLocalSide` the top view uses; a second visibility rule here would hand out intel the simulation says the side does not have. A drone riding a hull is skipped: it is glued to that hull's position.
  - `feed/FeedFilter.ts` (its two GLSL stages in `feed/shader.ts`) — the monitor: vignette, scan lines, grain, chromatic aberration, EW interference and dead-signal static, **one `Filter` with one fragment shader**. Not a chain, because every filter in Pixi is a full offscreen pass and this layer's history (the `Sprite`-mask incident in `TerrainView`) is what that costs. `resolution: 1`, `antialias: 'off'`, and the container carries `filterArea = app.screen` — without it Pixi measures the target's global bounds, and the wireframe terrain's bounds are the whole map. `?feed=0` prices the pass. Two of its effects are the *only* channel a simulation state has: `uJam` from `jamPressure` (until now `combat.jamMultiplier` was a smaller number inside two systems and nothing on screen) and `uStatic` from `isDisabled` (while a hull's electronics are down `FpvView` stops drawing the scene at all and the tube shows its own snow). **No backticks anywhere in the two shader strings** — they are template literals, and Vite is the only thing that catches one.
  - `glsl.ts` — `export const glsl = String.raw`, an identity tag. It exists for its *name*: the `boyswan.glsl-literal` extension highlights template literals tagged `glsl`/`vert`/`frag`, which is the only thing that makes these shaders readable in an editor. It adds no characters, so `precision highp float;` still literally starts the fragment source — Pixi's `ensurePrecision` honours a declaration only in that position and otherwise prepends **mediump**. Each effect owns its folder (`ground/`, `feed/`): the class or factory next to the GLSL it compiles, `index.ts` the barrel.
  - `camera.ts`'s `FpvCameraRig` — throttle lag, recoil, and the ring after a hit, all settled with `1 − exp(−dt/τ)` so the curve is the same at 30 fps and at 144. **The lag is longitudinal, not positional**: a possessed hull's heading snaps to the stick, so smoothing the eye's world position would swing it a quarter-turn away and take the machine off screen. **No engine changes were needed**: the bus has no damage event and `projectileFired` does not carry the shooter's id, so `FpvView.beat` *polls* the rising edge of `weapon.cooldownLeft` (a round leaving) and a fall in `hp` (one arriving). A kamikaze gets no recoil, and it falls out rather than being special-cased — no cooldown, no edge.
  - **Rounds in flight and the fire mark.** `FpvView` draws projectiles (a fat warm dash along the velocity — reused through the heat pass rather than a drawing path of its own, and untinted because a tracer belongs to nobody once it has left) and munitions, and brackets whatever `E` would shoot at. The bracket asks `manualFireTarget` — the function the trigger itself uses — never its own idea of what looks shootable. It is the only thing on the monitor that says a weapon can reach: a cannon's 180 px stops barely past the hull's nose on screen, so before this a pilot pressing `E` at a contour 300 px out got silence and concluded the key was broken. Marked in `palette.fpv.lock`, the same yellow as the top view's selection ring, because both mean "this is the one you singled out"; the shape differs (brackets, not a ring) since a contour already has an outline.
  - **Input is blocked while possessed** — `input/pointer.ts` asks the world (not the throttled `droneStatus` snapshot) and drops marquee, orders and base selection. The top view is hidden, so a click would order units at a point nobody can see. Keys are untouched; there is no separate exit gesture because cutting the view loose already bails the pilot out.
- `assets.ts` + `../config/sprites.ts` — `loadGameAssets`, `getRobotTexture(chassis)` (cached, optional crop frame) → placeholder fallback.
- `audio/sfx.ts` — the sound façade. Cues are **sample files** in `client/public/sfx/` played via `@pixi/sound` (`pixi.js` v8 itself ships no audio; `@pixi/sound` is a separate package). The library owns the AudioContext and puts an analyser + compressor in front of the destination, so there is no hand-built bus here. Also owns the **effects** switch and slider (persisted under `dd:sfxMuted`/`dd:sfxVolume`), applied per cue in `play()` rather than through `sound.muteAll`/`volumeAll` — those act on the shared context, which music also hangs off, and the two channels are settable separately. Driven by the bus, by `selectionAudio`, and by `ui/common/` — never by the renderer.
  - Table of aliases → files → mix balance: `client/src/config/sounds.ts` (**no `@pixi/sound` import there** — `config/` is reachable from `ui/`; it mirrors `sprites.ts`, `PUBLIC_BASE` included). Design briefs and replacement rules: `.docs/sfx/README.md`.
  - **Gotchas that cost real debugging.** `sound.exists()` is not a load guard — it goes true at registration, and `play()` before decoding *queues* the call, so a `ready` Set gates playback instead. `WebAudioContext.autoPause` defaults to true and suspends the whole context on window blur, which would kill the chat ping while the player is tabbed away — it is switched off in `init()`. Two `sound.play` calls in one synchronous tick start on the same output sample and sum coherently into one loud transient rather than reading as two sounds; hence the 70 ms `setTimeout` on `groupSelected`'s chassis layer and the `silent` prop on the chat send button. Bursty cues (`explosion`, `unitReady`) coalesce on a 120 ms window.
- `audio/selectionAudio.ts` — `attachSelectionAudio(world)`: one `useGameStore.subscribe` on `selectedRobotIds`/`selectedBaseId`, resolving the selection's distinct chassis in **one** pass over `world.with('robot')` against a Set of ids (`findById` is a linear scan — per-id lookups would make a big marquee quadratic).
- `audio/selectionSound.ts` — the pure decision (`selectionSoundFor`, `orderChassis`) behind that: base / single / group / none, deselection silent, and set-based comparison so a re-selection of the same robots in a different order says nothing. Tested in `selectionSound.test.ts` (node env, no Web Audio).
- `Grid.ts` — `createGround(terrain)`: variant A tiled across the field, variant B blended over it through a **procedural low-frequency mask** (a tiny canvas texture from `render/terrain/hash.ts`, stretched — the GPU's linear filtering does the smoothing), plus hash-scattered decals that skip blocked tiles and every base's clear margin. Seamlessness hides the *seam*, not the *period*, which is why one tile is not enough. Takes the terrain for that last step, so it must be rebuilt after the match context exists.
- `Camera.ts`, `layers.ts` (ground→units→projectiles→fx→overlay), `GameLoop.ts` (fixed step), `input/pointer.ts` (left-drag marquee with Shift-add; plain left click selects your own base under the cursor, else deselects; right click enqueues `SetRallyPoint` when a base is selected — on the base itself it clears — otherwise `AttackTarget`/`MoveRobots`. Orders go through `store.enqueueCommand`, never direct entity mutation, so both peers apply them on the same tick. No mouse panning: the camera follows the observer drone, flown with WASD/arrows).
- **Networking is not in this layer.** It lives in the `@drone-directive/net` workspace (transport + wire codec + validation) — see `net/README.md` and `.docs/multiplayer.md`. `GameApp` is the only file here that touches it: it builds a `LockstepSession` with `client/src/config/multiplayer.ts`'s `lockstepConfig`, and calls `worldHash` (now `client/src/engine/worldHash.ts`) for the desync probe. Don't add socket, codec, or schema code under `pixi/`.

## Rules & gotchas

- **Never run a browser-driven check alongside anything else heavy.** Checking this layer means a dev server plus a headless Chromium plus a GPU context; `npm test` is a few hundred seconds of saturated CPU. Run either, wait, then run the other — overlapping them can wedge the developer's machine, and it makes both readings worthless anyway (a perf p95 measured next to a test run is measuring the test run). Same for two captures at once.

- **No `!` in this layer.** `@typescript-eslint/no-non-null-assertion` is on for `client/src/pixi/**` (tests excluded). Entities come from `engine/ecs/queries.ts` already narrowed; an id lookup goes through `robotById`/`baseById`/`livingRobotById` or a guard from `engine/ecs/guards.ts`. See **dd-engine** for the archetype layer.
- **Snapshot throttling:** never push per-frame HP to the store (React re-render storm). Push on bus spawn/destroy + every `gameConfig.hud.snapshotEveryTicks`. Live HP shows via Pixi views reading the ECS world each frame.
- **Teardown:** unsubscribe bus + reactive queries, destroy views/graphics, on `useGameApp` unmount + `GameApp.destroy` (idempotent; StrictMode double-mounts).
- The persistent ECS `world` survives restarts (entities cleared/respawned) so the renderer subscribes once.
- **Online input filters must be symmetric.** `GameApp.stepOnline` screens both sides' batches with `isCommandFrom`, and `net` does the same with its schemas — a filter only one side applies is a desync. See **dd-net** before touching anything online.
- tsconfig: prefer const-map unions over `enum` and explicit fields over ctor param props; `import type`; no unused symbols.
