# Drone Directive — Pixi rendering + bridge (PixiJS v8, miniplex)

Owns the canvas and bridges the `GameEngine` to the store. **No React imports.** May import `client/src/engine/**`, the store (vanilla `useGameStore.getState()`), and — in `GameApp` only — `@drone-directive/net`.

## Files

- `GameApp.ts` — the boundary object React mounts (via `useGameApp`). Owns the `GameEngine`, `WorldRenderer`, camera, obstacle graphic. `init()`: `app.init` → `loadGameAssets` → build layers/camera → `new GameEngine()` → `WorldRenderer(layers, engine.world)` → `wireBus()` → pointer → loop. The loop `update` = `step(dt)`; `render` = `worldRenderer.sync(selectedIds, isVisibleToPlayer, now)` — `now` is **one** `performance.now()` read per frame, shared with the order marker and the hover reticle so everything animated on screen pulses in the same phase (and keeps pulsing while paused). `isVisibleToPlayer(e)` is the fog-of-war gate: player/neutral entities are always visible; an AI robot/base is only visible once `engine.context.intel.player` (see dd-engine's `TeamIntel`) has it in `visibleRobotIds`/`knownBaseIds`.
  - **step(dt):** apply store control flags (`restartRequested`→`engine.startMatch(config)`, `menuRequested`→`engine.toMenu()`, then `clearRequests()`); `engine.setPaused`; forward `drainCommands()`→`engine.enqueueCommand`; `engine.tick(dt)`; throttled `pushSnapshot`.
  - **wireBus():** `projectileFired`→`sfx.missileShot`/`sfx.cannonShot` (by `WeaponType`), `entityDestroyed`→`sfx.explosion` + snapshot + drop a selected base that just died (`selectBase(null)`), `entitySpawned`→snapshot + `sfx.unitReady` for own-side robots, `sceneChanged`→status + rebuild/clear obstacles + snapshot, `gameOver`→status won/lost.
  - **Selection audio is *not* on the bus.** Selection is store-only state, so `init()` also calls `attachSelectionAudio(engine.world)` (disposed in `destroy()`) — the second audio adapter.
  - **pushSnapshot():** projects `world.with('base'/'robot').entities` into store `BaseSnapshot`/`RobotSnapshot` DTOs + resources from `engine.context`.
- `render/WorldRenderer.ts` — **reactive queries**: `world.with(tag,'position')` per kind; `onEntityAdded`→create view, `onEntityRemoved`→destroy view; per-frame `sync(selectedIds, isVisible, now)` updates transforms/HP/selection/fog-of-war visibility. **A component can be a query**: `world.with('base','position','shield')` means "bases whose energy dome is up right now", so raising and losing a dome creates and destroys `ShieldDomeView` for free — including a base reaped with its dome still standing. That only works because the engine attaches/detaches `shield` through `world.addComponent`/`removeComponent`; a plain assignment would leave this query blind. (miniplex Query narrows to `With<...>`; cast to `Query<Entity>`.)
- `render/ShieldDomeView.ts` — the energy dome, on **`layers.fx`** (not `units`): it has to draw over the base, over the robots under it and over the rounds crossing it, and on `units` it would sit beneath both and read as a floor decal. `fx` is above `fog`, so it gates itself with the same `isVisible(base)` every other view uses. Three marks, because three things must be legible at once: a pulsing owner-coloured ring (it is there), a depletion arc (how much is left — what makes a 1000 hp pool readable without a number), and a white snap on any frame `shield.hp` fell (it is being hit *now*). That last one is inferred from a last-value compare, deliberately: absorbed rounds are far too frequent to spawn an entity for, and anything in the world lands in `worldHash`.
- `render/{BaseView,RobotView,ProjectileView,ExplosionView}.ts` — take an `Entity`, read components (`position/heading/hp/maxHp/chassis/weaponType/owner/effect`). HP bars live here (per-frame), not React. `RobotView.update(robot, selected, visible)` / `BaseView.update(base, visible, selected)` toggle `container.visible` for fog of war — the view stays alive (not destroyed) while hidden, so it snaps back instantly once known again. Both draw a `palette.selection.ring` selection outline (circle / footprint rect); `RobotView` additionally shows a `palette.vision.spotted` highlight ring on enemy robots whenever `visible` is true (i.e. currently detected), and a `palette.blast.zone` radius ring on bomb-armed units. Only own-side views are `eventMode: 'static'` (enemy views stay pointer-transparent so right-clicks reach the stage → attack order): `RobotView` handles click-select + double-click "select all with this weapon"; `BaseView` handles double-click → `setBuildDialogOpen(true)` only — *selecting* a base is the stage handler's job in `input/pointer.ts`, because a click here bubbles anyway and would be undone by the stage's deselect. Both share `input/doubleClick.ts`'s `DOUBLE_CLICK_MS` and let single clicks bubble to the stage. **A status effect needs its own picture or it doesn't exist to the player** — the `dew` knock-out is drawn on three independent channels because a weapon that deals no damage has no explosion to borrow: a fat bolt in `ProjectileView` (`kind: 'dew'`), an `EffectKind.Emp` discharge ring in `ExplosionView` (spawned by `spawnEmpBurst`, sharing the `explosion` archetype so ageing and the view lifecycle come free), and a per-frame crackling cage + dimmed hull in `RobotView.drawStunned`. `ExplosionView` branches on `effect.kind`; absent = `Blast`, the original fireball. `ShieldBreak`/`ShieldExpire` (spawned by `spawnShieldEnd`, same borrowed archetype) are drawn as visual opposites — a shell coming apart into shards versus one ring contracting softly — because the player must know at a glance whether the dome was beaten down or simply ran out. **A base shoots, so it has to look like it does:** `BaseView` draws the built-in missile launcher over the body and rotates it by `base.heading` (written by `taskSystem`'s turret pass) — a projectile appearing out of a building with no visible source reads as a bug, the same lesson the `dew` channels above encode. **`DroneView` is owner-aware, unlike `teamTint`'s rule:** there is only *one* drone art set, where robots and bases have two, so an untinted enemy drone would look pixel-for-pixel like your own in a 1v1. The local side keeps the authored look; every other side is recoloured with `ownerColor`.
- `render/RallyView.ts` — GameApp-owned (not ECS-bound) `Graphics` in the `overlay` layer, drawing the **local side's** rally flags plus a leader line to the base that owns each. Both peers hold every base's `production.rally`, so this filter is what keeps the opponent's gathering point off screen. Redraws only when a marker moves.
- `render/ObstaclesView.ts` — `createObstaclesGraphic(terrain)` from `engine.context.terrain` (rebuilt per match on `sceneChanged: game`); one tile sprite per blocked cell, picked from `terrainSprites` by `TerrainKind` (mountain/crater), flat Graphics fill as fallback.
- `assets.ts` + `../config/sprites.ts` — `loadGameAssets`, `getRobotTexture(chassis)` (cached, optional crop frame) → placeholder fallback.
- `audio/sfx.ts` — the sound façade. Cues are **sample files** in `client/public/sfx/` played via `@pixi/sound` (`pixi.js` v8 itself ships no audio; `@pixi/sound` is a separate package). The library owns the AudioContext and puts an analyser + compressor in front of the destination, so there is no hand-built bus here. Also owns mute/volume (`sound.muteAll`/`volumeAll`, persisted under `dd:sfxMuted`/`dd:sfxVolume`). Driven by the bus, by `selectionAudio`, and by `ui/common/` — never by the renderer.
  - Table of aliases → files → mix balance: `client/src/config/sounds.ts` (**no `@pixi/sound` import there** — `config/` is reachable from `ui/`; it mirrors `sprites.ts`, `PUBLIC_BASE` included). Design briefs and replacement rules: `.docs/sfx/README.md`.
  - **Gotchas that cost real debugging.** `sound.exists()` is not a load guard — it goes true at registration, and `play()` before decoding *queues* the call, so a `ready` Set gates playback instead. `WebAudioContext.autoPause` defaults to true and suspends the whole context on window blur, which would kill the chat ping while the player is tabbed away — it is switched off in `init()`. Two `sound.play` calls in one synchronous tick start on the same output sample and sum coherently into one loud transient rather than reading as two sounds; hence the 70 ms `setTimeout` on `groupSelected`'s chassis layer and the `silent` prop on the chat send button. Bursty cues (`explosion`, `unitReady`) coalesce on a 120 ms window.
- `audio/selectionAudio.ts` — `attachSelectionAudio(world)`: one `useGameStore.subscribe` on `selectedRobotIds`/`selectedBaseId`, resolving the selection's distinct chassis in **one** pass over `world.with('robot')` against a Set of ids (`findById` is a linear scan — per-id lookups would make a big marquee quadratic).
- `audio/selectionSound.ts` — the pure decision (`selectionSoundFor`, `orderChassis`) behind that: base / single / group / none, deselection silent, and set-based comparison so a re-selection of the same robots in a different order says nothing. Tested in `selectionSound.test.ts` (node env, no Web Audio).
- `Camera.ts`, `Grid.ts`, `layers.ts` (ground→units→projectiles→fx→overlay), `GameLoop.ts` (fixed step), `input/pointer.ts` (left-drag marquee with Shift-add; plain left click selects your own base under the cursor, else deselects; right click enqueues `SetRallyPoint` when a base is selected — on the base itself it clears — otherwise `AttackTarget`/`MoveRobots`. Orders go through `store.enqueueCommand`, never direct entity mutation, so both peers apply them on the same tick. No mouse panning: the camera follows the observer drone, flown with WASD/arrows).
- **Networking is not in this layer.** It lives in the `@drone-directive/net` workspace (transport + wire codec + validation) — see `net/README.md` and `.docs/multiplayer.md`. `GameApp` is the only file here that touches it: it builds a `LockstepSession` with `client/src/config/multiplayer.ts`'s `lockstepConfig`, and calls `worldHash` (now `client/src/engine/worldHash.ts`) for the desync probe. Don't add socket, codec, or schema code under `pixi/`.

## Rules & gotchas

- **Snapshot throttling:** never push per-frame HP to the store (React re-render storm). Push on bus spawn/destroy + every `gameConfig.hud.snapshotEveryTicks`. Live HP shows via Pixi views reading the ECS world each frame.
- **Teardown:** unsubscribe bus + reactive queries, destroy views/graphics, on `useGameApp` unmount + `GameApp.destroy` (idempotent; StrictMode double-mounts).
- The persistent ECS `world` survives restarts (entities cleared/respawned) so the renderer subscribes once.
- **Online input filters must be symmetric.** `GameApp.stepOnline` screens both sides' batches with `isCommandFrom`, and `net` does the same with its schemas — a filter only one side applies is a desync. See **dd-net** before touching anything online.
- tsconfig: prefer const-map unions over `enum` and explicit fields over ctor param props; `import type`; no unused symbols.
