# Drone Directive — Game core (ECS + scenes)

Pure, framework-free. **Never import React, Pixi, or the store here** — nor `@drone-directive/net` or `@drone-directive/protocol`: the engine must not learn about the wire. It may import `@drone-directive/types` (the shared value types) and `client/src/config/**`. Uses **miniplex** for ECS.

## Layout

- `ecs/entity.ts` — `Entity` = a bag of optional components; boolean tags (`base/robot/projectile/explosion/munition`) drive `world.with(...)` archetype queries. Components: `owner, position, heading, hp, maxHp, chassis, weaponType, movement{speed,state,destination,path,goal}, weapon{range,damage,cooldown,cooldownLeft,explosionRadius,...,salvo}, sightRange, script{programId,blackboard}, targetId, threat{attackerId,underFireLeft}, production{queue,progress,autoBuild,autoBuildPreset,autoBuildStep,defaultTask,rally}, footprint, velocity, damage, ttl, sourceId (projectile shooter / munition launcher), effect{age,duration,maxRadius?}, regenLock{left} (passive repair paused by a recent hit — bases carry it too), shield{hp,left} (a base's one-shot energy dome, present only while it stands — an archetype tag, see below), shieldSpent (that charge is gone, and outlives the dome)`.
- `ecs/world.ts` — `createEcsWorld()`, `clearWorld()`.
- `ecs/factory.ts` — `spawnBase/spawnRobot/spawnDrone/spawnMunition/spawnProjectile/spawnExplosion/spawnEmpBurst/spawnShieldEnd` (`world.add(...)`); `spawnRobot` sets `sightRange` from `gameConfig.robots.chassis[chassis].sight` (per-chassis); `spawnBase` sets it from `gameConfig.bases.sightRange`. Both build their `weapon` through the shared `weaponComp(type)` — a new weapon stat is added in one place, not two.
- `systems/*` — each is `(ctx: GameContext, dt?) => void`, iterating `ctx.world.with(...)`: `commands, economy, ai, production, vision, task (a folder, task/{index,resolver,outcomes,roam,advancing,types}.ts, exports isAdvancing/ADVANCING_TASKS/centroidOf plus its taskSystem), drone, movement (exports setGoal/clearGoal), separation, combat (exports canEngage/needsLineOfSight/launchSalvo/applyDamage/detonateBomb), munition, reap (returns bool), shield (exports isShielded/canRaiseShield/canActivateShield/raiseShield/absorbShieldDamage), regen, droneRespawn, explosion, fog`, plus the non-system helpers `status.ts` (the two status effects), `aiDrone.ts` (`pilotDrone`, called by `ai.ts` rather than by the scene) and `targeting.ts` (`isEnemy/findById/baseFootprintContains/distanceToBase/enemyRobots/enemyBases/enemyAirTargets/knownEnemyRobots/knownEnemyBases/knownEnemyAir/isKnownTo/ownBase/isTargetableDrone/isAirTarget/nearest`).
- `game/context.ts` — `GameContext { world, bus, resources, terrain, obstacles, sightBlockers, navObstacles, rng, difficulty, config, commands, ai, intel }`; `createGameContext`. **Three terrain grids, one source:** `terrain` is the per-tile `TerrainKind` (rendering); `obstacles` = impassable (mountains **and** craters — pathfinding, roam targets); `sightBlockers` = fire-blocking (mountains **only** — LOS + projectile collision, so shots cross a crater robots must drive around); `navObstacles` = `obstacles` + living base footprints. Pick the grid by the question you're asking, never by habit. Globals (resources/obstacles/rng/intel) live here, NOT on entities. `createGameContext` also rolls the per-match enemy corner (`applyEnemyCorner(ENEMY_CORNERS[…])`, player fixed bottom-left) from the match rng — it must stay ahead of `generateObstacles`, which clears/carves around `gameConfig.bases.placements`. `intel: { player: TeamIntel; ai: TeamIntel }` is each side's shared detection state.
- `game/events.ts` + `eventBus.ts` — typed `EventBus<GameEvents>`; discrete events only (`entitySpawned/entityDestroyed/baseDestroyed/projectileFired/shieldRaised/shieldEnded/sideEliminated/gameOver/sceneChanged`).
- `game/scene.ts` + `scenes/{menuScene,gameScene}.ts` — `Scene {enter/update/exit}` + `SceneManager`. `GameScene.enter` builds the world (bases/starters per difficulty + base settings); `update` runs the system pipeline then checks game-over.
- `game/engine.ts` — `GameEngine`: persistent `world` + `bus`; `tick(dt)` (skips when paused), `startMatch(config)`, `toMenu()`, `setPaused`, `enqueueCommand`, `get context`.
- `worldHash.ts` — FNV-1a fingerprint of the simulated world (`(world) => number`), used by the online layer as a desync probe. Lives here, not in `net`, because it reads the ECS world; it must hash **simulation state only** — never anything derived from `localSide` (fog, selection, camera), which legitimately differs per client.
- Reused pure helpers: `pathfinding.ts` (`findPath`, `nearestFreeTile`), `obstacles.ts` (`generateObstacles` → a `TerrainGrid`, kind rolled per cluster; `movementGrid`/`sightGrid` derive the two boolean grids; `isBlockedGrid`, `hasLineOfSight`, `tileOf`, `tileCentre`), `economy.ts` (`buildCost/canAfford/spend/stepEconomy` — operate on `ResourcePool`), `tasks/taskDefinitions.ts` (`make*`, `scriptForTask(pos, task)` → a script carrying a `programId` + blackboard).

## Behaviour model (directive programs)

Robot behaviour is a **priority-ordered directive list** ("when → do"), not a single task. Types live in `@drone-directive/types/tasks` (`BehaviorCondition`, `BehaviorAction`, `Directive`, `Program`); the built-in programs (the JSON-describable scenarios) live in **`config/programs.ts`**, keyed by `TaskType` (the id the UI/settings pick — includes `Scout`, "Search & Detect"). `systems/task.ts` is the resolver: each tick it walks a robot's program and takes the **first move intent and first fire intent independently** (so a robot can `evade` while `attackAttacker` returns fire), then sets the goal + `targetId`. `combat.ts` fires at `targetId` whenever in range+LOS+cooldown — **decoupled from movement**. Being hit records `threat{attackerId,underFireLeft}` (drives the `underFire` condition, decayed in `task.ts`). Add a reaction = add a directive; add a program = add a `TaskType`/registry key.

**Build presets (auto-production series).** `config/buildPresets.ts` — `Record<BuildPresetType, BuildPreset>` (`{id, label, sequence: BuildOrder[]}`), `getBuildPreset(id)` (falls back to `Tracks`). A base's `production.autoBuildPreset` (id) + `autoBuildStep` (cycle cursor) drive `productionSystem`'s auto-refill: it queues `sequence[autoBuildStep % sequence.length]`, advancing the step only when the order is actually affordable (an unaffordable step just retries next tick, doesn't skip). A single-chassis auto-build is just a length-1 sequence. `BuildOrder.task` (see `@drone-directive/types/entities`) may be set per-step; extend the roster by adding a key, matching `config/programs.ts`'s "add a program by adding a key" pattern.

**Rally point.** `production.rally` (`Vec2 | null`, set by the `SetRallyPoint` command) is where a base's new robots gather. `productionSystem` applies it to exactly two programs: `Guard` gets the rally as its `blackboard.guardPos` (so it walks there and patrols the flag, not the factory door), and `Idle` gets an explicit `setGoal` — Idle emits no move intent of its own, which is what lets a manually issued goal survive `taskSystem`. Every other program overwrites the goal on the same tick (`taskSystem` runs after `productionSystem`), so a rally point would never reach it. The check is on the _resolved_ `script.programId`, not the requested task, so a radar refused an attack program still rallies as Idle.

**Weapons (`gameConfig.robots.weapons[type]`).** Each entry is `{range,damage,cooldown,explosionRadius,sightMultiplier,jamRadius,canHitAir,freezeDuration,salvo}`. `cannon`/`missiles` fire projectiles (`combat.ts`). `bomb` (kamikaze) has `explosionRadius > 0`: `combat.ts`'s `detonateBomb` deals `damage` to every enemy robot/base within the blast (AOE), spawns an oversized explosion (`spawnExplosion(pos, radius)` → `effect.maxRadius`), and sets its own `hp=0` (reap removes it). Its `range` (60) must exceed a base's half-footprint so it triggers at the base edge; the blast radius does the killing. `radar` has `sightMultiplier: 2` (scales the chassis `sight` in `spawnRobot`) and `range 0` → never engages, only spots. `dew` (directed energy) has `damage 0` + `freezeDuration > 0`: an ordinary projectile that knocks the robot it hits out instead of hurting it (see the status effect below), and flies straight over bases (a zero-damage round is never absorbed by one). `fpv` has `salvo > 0`: instead of a round it releases that many `munition` entities, each carrying the weapon's own `damage` — see the air layer below. Its `range` (4000) means "anywhere", so **two extra gates in `fireWeapon` are what actually bound it**: `isKnownTo` (someone must have eyes on the target *right now*) and `withinMunitionReach` (`munition.speed × flightTime` = 1680 px, which does **not** span a medium or large map corner-to-corner). Both also apply to manual fire from a possessed hull. Add a weapon = add a `WeaponType` key + a `weapons`/`weaponCost` entry; damage-dealing paths key off `explosionRadius`/`range`/`freezeDuration`/`salvo`, not the enum — `combat.ts` exports the two duck-typed tests every path shares: `canEngage(w)` ("is this thing armed") and `needsLineOfSight(w)` (false for a launcher, whose drones fly over terrain — honoured by `fireWeapon`, `engageOutcome` **and** `guardOutcome`), and `drone.ts`'s manual fire uses both.

**Bases shoot back (`gameConfig.bases.weapon`).** Every base carries one built-in launcher — `missiles` today — as an ordinary `weapon` component, so it goes through the same `fireWeapon` a robot does; `combatSystem` simply runs two queries (`robot` then `base`), because the archetype tag is the only difference. Target selection lives where every other `targetId` is set, in `taskSystem`: a small pass after the robot loop calls `baseTurretTarget`, which is **air-first** (spotted enemy drone before any ground robot) and reads `knownEnemyAir`/`knownEnemyRobots`, so a building is no more omniscient than a unit. Two consequences are deliberate: while a drone is in reach the battery is busy with it, so a kamikaze gets an easier run; and an enemy `ew` halving the base's 260 px sight to 130 blinds the battery at the outer edge of its own 170 px range. Range is measured from the footprint **centre** — so is a robot's shot at the base — which keeps that duel even. The same pass writes `base.heading`, which is render-only (`BaseView`'s launcher tracks it) and therefore stays out of `worldHash`.

**The base's energy dome (`systems/shield.ts`).** One per base per match, every side including bots, 20 s, 1000 hp, mending 20 hp/s while it stands (`gameConfig.bases.shield`). It is **armor, not a wall**: nothing in pathfinding, LOS or collision changes, a kamikaze drives right under it, and robots beneath it are as exposed as they were — all it does is take the damage aimed at the _building_, from any source at any position, with the overkill on the breaking hit spilling through. That single unconditional rule is why absorption lives in `applyDamage` (there is no "inside the dome" state to special-case) and why `detonateBomb` needed no change at all. `stepProjectiles` gets one extra branch, gated on `p.targetId === b.id` exactly like `hitsAimedDrone`, which decides only _where a round is seen to stop_ — a blanket radius test there would eat every shot fired at a robot standing under the dome. Absorbed damage deliberately does **not** `blockRegen` the base: it was never hit. Two components carry it — the transient `shield{hp,left}` and the permanent `shieldSpent`, which outlives it because there is no second charge. **`shield` is an archetype tag** (`world.with('base','position','shield')` = "domes standing now", which is also the renderer's view lifecycle), so it may only be attached/detached via `world.addComponent`/`world.removeComponent` — the _only_ place in the repo that uses them. A plain `base.shield = {...}` compiles and even absorbs correctly, but no query sees it: the dome never ticks and never draws. `shieldSystem` runs **between `combat` and `reap`** — after combat so a dome beaten to zero shatters the tick it broke; before reap so a base finished off by the spill still shows its dome coming apart. Both axes plus `shieldSpent` are in `worldHash`: the dome is the one piece of state _not_ observable through hp, because stopping hp from moving is its whole job. `canActivateShield` (own base, unspent, a **known** enemy robot inside `sightRange`) gates only the HUD tile; `applyCommand` deliberately does not re-check it — pre-casting merely wastes the player's own charge. Bot policy is `maybeRaiseShield` in `ai.ts`, and it counts `knownEnemyRobots` rather than the omniscient `nearbyEnemyCount`: this is the one control both sides hold, so both pay for scouting.

**Status effects (`systems/status.ts`).** Two today. The second is the repair lock — see the passive-repair paragraph below. The first is the directed-energy knock-out, an optional `disabled?: {left}` component. `isDisabled`/`applyDisable`/`decayDisabled` are the only way it is touched; `applyDisable` takes the **max**, so focused fire extends rather than stacks. It decays once per tick in `taskSystem` (next to `threat.underFireLeft`), _before_ the guard, so the tick a robot recovers on is the tick it acts again. While it holds, the robot does nothing at all: `task.ts` skips its program (which is why an order issued to it sticks and runs on recovery), `movement.ts` skips it but keeps `prevX/prevY/stuckTime` current so anti-jam doesn't read the standstill as a jam, `combat.ts` neither fires nor reloads it, `vision.ts` drops it as scout _and_ as jammer, `drone.ts` won't let the drone land on it and freezes an already-possessed hull, `ai.ts` leaves it out of task reassignment. Separation deliberately still pushes it, so a frozen cluster never becomes a wall. It is part of `worldHash` — a status effect peers can disagree about is a desync one tick later. **The catch a new status effect must also handle:** `Idle` only returns fire (`underFire` → `attackAttacker`), so silencing an enemy would _protect_ it from idle guns once the 1.2 s window lapsed — hence the `disabledEnemyWithin` → `finishDisabled` directive in `Idle` (fire-only, so "idle doesn't chase" holds; `disabledInRange` requires `damage > 0`, so a `dew` gun doesn't burn its reload re-freezing).

**Bot policy for support weapons (`systems/ai.ts`).** A unit that can't kill needs its own rule or the bot throws it away. `ensureEwRobot` keeps exactly one `ew` jammer alive on `DefendBase`; `positionDewUnits` re-decides every tick where each `dew` hull stands — `DefendBase` at home unless `gameConfig.ai.dewEscortMin` **armed** (`weapon.damage > 0`) friendlies are already advancing (`isAdvancing`), `Overwatch` while `cooldownLeft > 0` (fall back behind the group's centroid instead of standing on the firing line through a 5 s reload), else `AttackRobots`. `positionFpvUnits` pins every `fpv` carrier to `Guard` at home for the whole match: its range already covers the map, so it need never move — marched out with a wave it would walk an artillery piece into a firefight, and on `DefendBase` it would only shoot at what is already on its doorstep, the one place its reach is worth nothing. All three weapons are excluded from `assignUnits`' group slice and from `mobilizeDefense`, so their own pass is the only thing that assigns them. Reassign **only on an actual program change**: a per-tick rewrite would churn the blackboard and restart the patrol leg in progress.

**The air layer (`munition` + `isAirTarget`).** Two entities fly: the observer drone (`drone`, one per side, the side's eye) and the FPV strike drone (`munition`, five per salvo, single-use). They wear **different tags on purpose** — `droneRespawnSystem`, `DroneView`, `store.droneStatus` and possession all read `drone` as "this side's eye", and munitions would read as lost eyes — so what they share is a predicate, not a component: `isAirTarget(e)` in `targeting.ts` is what "air" means everywhere (`enemyAirTargets` → `visionSystem`'s `intel.visibleAirIds` → `knownEnemyAir` → `airTarget`/`baseTurretTarget`/`hitsAimedAir`). **`intel` carries two timescales for bases and they are not interchangeable:** `knownBaseIds` only grows (a building found once stays found — that is what lets a unit be ordered to attack it without an escort keeping eyes on the door), while `visibleBaseIds` is this tick's truth. Directives read the first; anything needing a live observer reads the second. Gating a salvo on `knownBaseIds` silently switches the reconnaissance requirement off after the first glimpse. Only a `canHitAir` weapon may engage either, and only the flyer it **aimed at** is hit (`hitsAimedAir`) — a blanket radius test would have every crossfire sweep the sky. `munitionSystem` owns a strike drone end to end and runs **after `combatSystem` (which launches them) and before `shieldSystem`** (so a hit on a base reaches the dome in the same tick's accounting as a shell). Five ways it dies, checked in this order before it may move: hp at zero (anti-air connected this tick), inside a living non-`disabled` enemy `ew`'s `jamRadius` (the jammer's **second** job, and `fpv`'s hard counter), `ttl` expired, target gone, contact. Its `targetId` is locked at launch and never re-picked, its `sourceId` is the **launcher** (the munition is destroyed on impact, so naming itself would leave the victim returning fire at nothing), and it never reaches `reapSystem` — no `entityDestroyed`, no death sound, nothing referencing it. `ttl` stays out of `worldHash` deliberately: a munition moves every tick, so any disagreement shows up in the entity set on the next one.

**The bot flies a drone too (`systems/aiDrone.ts`).** Every side gets an observer drone, bots included — the whole drone stack was already owner-generic (`droneSystem` reads `ctx.droneControl[owner]`, `visionSystem` counts a drone as a scout for its side, `airTarget` lets missile robots engage an enemy one), so a bot needed a pilot, not a mechanism. `pilotDrone(ctx, owner, state)` is called first thing in `runBot` (before the base check, so a side losing its base doesn't leave a stale `dir` flying the wreck), and `aiSystem` runs before `droneSystem` in the same tick, so nothing moved in the pipeline. It writes only `dir` and **never** `possessPulse`/`firePulse` — that is the bot's whole handicap, enforced structurally rather than by a flag, and it costs the bot dearly: `isTargetableDrone` only exempts a drone riding a hull, so a bot's drone is permanently exposed to anti-air fire. Three rules in priority order: break contact from an enemy `canHitAir` robot or enemy base within `ai.droneDangerRange` (reads the raw world, not intel — this is flinching from a threat, not aiming at one, and a scout that must _spot_ a launcher first just dies); else lead its own advancing group (`isAdvancing`) by `ai.droneScoutLead`, mirroring `overwatchOutcome`'s centroid but forward; else sweep to `AiState.droneWaypoint`, re-picked on arrival only — drawing from `ctx.rng` every tick would jitter the path and desync-proof nothing. Under `ai.droneCautiousHp` it stops scouting and pickets home instead: drones never repair, so a damaged one is spent goods.

**A bot never leaves a robot on `Idle` (`systems/ai.ts`).** `Idle` is passive — it returns fire only at whoever already hit it, only for `underFireDuration`, and `attackAttacker` contributes no move intent, so an idle robot shot from beyond its own range never closes. That makes an idle unit both a discount target and dead weight, so bot policy has no `Idle` in it at all: `ensureFactoryDefault` pins the bot base's `production.defaultTask` to `DefendBase` (its build preset sets no per-step task), and `sweepIdle` at the end of `runBot` catches anything that reached `Idle` by another route (starter robots, a program refused for its weapon). `assignUnits` fills a `guardQuota` defence line on `DefendBase` — existing defenders first, so the quota doesn't churn — and puts the surplus on `GroupAttack`; `REASSIGNABLE` (`Idle | DefendBase`) is the pool it draws from, since everything else is mid-task. `forcePosture` still overrides: `defensive` holds everyone at home, `offensive` sends the surplus straight out on `AttackBase` without waiting for a group.

**`DefendBase` and `GroupAttack` (`config/programs.ts` + `task.ts`).** `DefendBase` differs from `Guard` in where it looks: the intercept test is "a known enemy within `behavior.defendBaseRadius` of **my own base**", not "within **my** weapon range", and the response is `engageOutcome` — it _moves_. So the whole defence line converges on one intruder, and goes back on patrol (`behavior.defendPatrolRadius`) once it's gone, rather than chasing. An unarmed hull (`weapon.range <= 0`) skips the intercept and only patrols, which is why the program is refused to nobody. `GroupAttack` gathers at base until `behavior.groupAttackSize` allies on the same program and **not yet committed** are within `behavior.groupGatherRadius`, then latches `blackboard.committed` on the **whole group in one pass** and advances; while gathering it runs `DefendBase`. Two invariants carry it: count only uncommitted units (or a departed wave keeps the threshold satisfied and every new robot trickles out alone) and commit the group at once (or the shrinking pool strands the tail below the threshold forever). `committed` is never cleared — a wave that takes losses must not turn around. `isAdvancing(e)` (exported from `task.ts`) is the "is this unit pushing" test everywhere, since `GroupAttack` is only _sometimes_ advancing; `ADVANCING_TASKS` remains the plain-program set behind it.

This replaced a staged-wave mechanic in `ai.ts` (`state.groupTarget`, `rollAttackGroup`, `ai.attackGroupMin/Max`) that parked surplus units on `Idle` until the pool reached a per-wave random size of up to 10 — unreachable once `production.maxRobots`, the guard quota, the EW jammer and the `dew` hull took their share, so a high roll left the surplus idle at base for the rest of the match. Keep the threshold inside the program: it can see the force it is actually counting.

**Passive repair (`systems/regen.ts`).** Robots and bases slowly mend themselves — `gameConfig.robots.regenPerSecond` (0.2 = 1 hp/5 s) and `gameConfig.bases.regenPerSecond` (0.4, twice that). It runs **after `reap`**, so nothing at hp<=0 can be pulled back before the reaper takes it, and it is the one system that deliberately does _not_ skip a `disabled` robot (repair is passive, not an action). Every hit suspends it for `gameConfig.combat.regenDelay` seconds via the second status effect, `regenLock{left}` (`blockRegen`/`canRegen`/`decayRegenLock`, max-not-stack like `applyDisable`, decayed in `regenSystem` because bases carry it and `taskSystem` only walks robots). Setting it is one of the two things **`combat.ts`'s exported `applyDamage(e, amount, sourceId?)`** does — it is the single place hp is subtracted, and the other thing is stamping `threat` on robots; a bomb zeroing its own hp is _not_ damage and stays outside it. `hp` is now fractional, which is why `worldHash` quantises it to 1/1000 rather than rounding to whole points — the lock needs no hash field of its own, since it is only observable through hp.

**No omniscience — enemies must be detected.** `enemyRobotsExist`/`enemyBasesExist`/`enemyRobotWithin` and the `attackNearest*` actions all read `targeting.ts`'s `knownEnemyRobots`/`knownEnemyBases`, not the raw (fully-omniscient) `enemyRobots`/`enemyBases`. "Known" is per-team, computed once per tick by `systems/vision.ts` (`visionSystem`) from each living robot's _and base's_ `sightRange` (robots and bases contribute vision equally), into `ctx.intel.{player,ai}`: `visibleRobotIds` is recomputed fresh every tick (an enemy robot drops out the instant no ally can see it — no memory, since it moves), `knownBaseIds` only grows (a base doesn't move, so discovery is permanent). Sight radii are config, not uniform: `gameConfig.robots.chassis[*].sight` per chassis type, `gameConfig.bases.sightRange` for bases. The `search` action (used as the `AttackBase`/`AttackRobots`/`Scout` fallback once nothing is known) roams to a random reachable tile via `ctx.rng` + `pathfinding.nearestFreeTile`, picking a new one on arrival. `guard` (Guard's action) is the same roam loop bounded to `gameConfig.behavior.guardPatrolRadius` around `blackboard.guardPos` (perimeter patrol, not standing still) — both share `blackboard.roamTarget` and a `roamOutcome` helper in `task.ts`.

## System pipeline order (GameScene.update)

`commands → economy → ai → production → vision → task → drone → movement → separation → combat → munition → shield → reap → regen → droneRespawn → explosion → fog → game-over`. Vision runs right before task (so directives act on this tick's fresh detection state); `drone` runs right after task so it can overwrite a possessed robot's `targetId` and keep its fire manual — and, because `ai` already ran, a bot's `DroneControl` is fresh in the same tick; `separation` (pushes overlapping robots apart — see `systems/separation.ts`) runs right after movement so no two robots settle on the same coordinates; firing runs after movement/separation (final positions); `munition` sits right after `combat`, which launches strike drones, so anti-air that connected this tick removes one before it can land its hit; `shield` sits between `munition` and `reap` (see the dome below), which also puts a munition's hit on a base into the same tick's dome accounting as a shell; `regen` after `reap` so nothing is healed back over the line, and `droneRespawn` after it too so a drone lost this tick starts its clock this tick; `fog` last, off settled positions. Keep this order when adding systems.

## Contracts

- **Determinism:** fixed 30 Hz step + seeded `ctx.rng`. Don't use `Math.random` in systems — use `ctx.rng`.
- **Commands** are the only UI→core intent channel (`ctx.commands`, drained by `commandsSystem`). **EventBus** is engine→observers only (supplement; not for per-frame state).
- Navigation: set via `setGoal(ctx, entity, x, y)` / `clearGoal(entity)` (pathfinds around obstacles); never write `movement.destination` directly.
- When removing entities while iterating a query, snapshot first (`[...world.with(...)]`).

## Gotchas (tsconfig)

- **Prefer** const-map unions (`@drone-directive/types/enums`, the shared `types` workspace) over a TS `enum`, and explicit field assignment over constructor parameter properties (see the scenes) — conventions, not compiler-enforced bans.
- `verbatimModuleSyntax`: `import type` for types. `noUnusedLocals/Parameters`. `as const` config → annotate reassigned fields (`: number`).
