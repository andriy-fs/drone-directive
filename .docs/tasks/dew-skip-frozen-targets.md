# ОНЭ не тратит выстрел на уже замороженную цель — implementation plan

## Context

`ОНЭ` — это `WeaponType.Dew` (`types/src/enums.ts:47`), оружие направленной энергии: `damage: 0`,
`freezeDuration: 8`, `cooldown: 5` (`client/src/config/gameConfig.ts:197-206`). Попадание вызывает
`applyDisable`, который **не стакается**, а берёт `Math.max` (`systems/status.ts:30-34`). Значит
выстрел по цели, у которой ещё 7.9 с заморозки, покупает ~0.1 с — при пятисекундной перезарядке это
чистая потеря темпа: пока ОНЭ перезаряжается, ничего нового он вывести из строя не может.

Сейчас ОНЭ выбирает цель ровно как обычная пушка — `nearest(...)` по `knownEnemyRobots`, без всякой
оглядки на `isDisabled`. Единственное место в движке, знающее про заморозку при выборе цели, —
`disabledInRange` (`systems/task.ts:216`), и оно решает **обратную** задачу (добить беспомощного),
причём явно исключает оружие с `damage <= 0`, чтобы ОНЭ туда не попал. Поэтому «ОНЭ не
перезамораживает» сегодня работает **только** на программе Idle — и то побочно, как следствие того,
что у Idle других директив с огнём нет.

Проблемные пути (все ведут в `engageOutcome` → `fire: target.id`):

| Место | Программа |
|---|---|
| `task.ts:249` `attackNearestRobot` | AttackRobots, AttackBase, Scout, GroupAttack |
| `task.ts:287-293` `defendBaseOutcome` | DefendBase (+ несобранный GroupAttack) |
| `task.ts:499` `guardOutcome` | Guard |
| `task.ts:348` `groupAttackOutcome` | GroupAttack |
| `task.ts:382` `attackAttackerOutcome` | ответный огонь во всех боевых программах |

`ai.ts:positionDewUnits` (:118-139) штатно ставит ботовский ОНЭ на `AttackRobots`/`DefendBase`, так
что бот попадает в баг постоянно.

**Цель:** для оружия, чей единственный эффект — вывод из строя, уже замороженный враг перестаёт быть
целью автоматического выбора. Ни огня, ни сближения. Оружие остаётся заряженным (`cooldownLeft`
тикает независимо от наличия цели), поэтому следующего, кто очнётся или подойдёт, ОНЭ накрывает
мгновенно — это строго выгоднее, чем спустить перезарядку впустую.

Принятые решения:

1. Если все видимые враги заморожены — **держать выстрел**, не бить «хоть куда-то».
2. **Явный приказ игрока — закон**: `AttackTarget` (правый клик) и ручное пилотирование
   (`drone.ts:fireManual`) фильтр не трогает. Это согласуется с уже задокументированным решением в
   `pixi/input/hitTest.ts:49-50` («deliberately ignores `isDisabled`»).
3. **Без порога**: любая ненулевая заморозка дисквалифицирует цель. Никакого нового поля в
   `gameConfig` и никакого тюнинга; цель с остатком 0.1 с станет кандидатом через 0.1 с.

## Изменения

### 1. Общее правило — `client/src/engine/systems/targeting.ts`

Один новый экспортируемый предикат рядом с остальными хелперами выбора цели. Утиная типизация по
характеристикам оружия — ровно как в `canEngage` (`combat.ts:75-77`), а не `switch` по `WeaponType`:

```ts
/**
 * Оружие, единственный эффект которого — вывод из строя (`dew`).
 */
function isDisabler(w: WeaponComp | undefined): boolean {
  return !!w && w.damage <= 0 && w.freezeDuration > 0;
}

/**
 * Даёт ли выстрел `shooter` по `target` хоть что-нибудь прямо сейчас.
 * Для обычного оружия — всегда да. Для «глушилки» два случая пустые:
 * цель уже выведена из строя (`applyDisable` берёт максимум, не сумму), и
 * цель — здание (у него нет экипажа, `stepProjectiles` пропускает такой
 * снаряд сквозь базу — см. combat.ts:210-213).
 */
export function worthShooting(shooter: Entity, target: Entity): boolean {
  if (!isDisabler(shooter.weapon)) return true;
  return !target.base && !isDisabled(target);
}
```

Импорт `isDisabled` из `./status` — цикла нет (`status.ts` тянет только тип `Entity`).
`WeaponComp` — `import type` из `../ecs/entity` (`verbatimModuleSyntax`).

**Почему в предикате есть ветка `target.base`.** Без неё правка ломает существующее поведение: в
`AttackRobots` директива `attackNearestRobot` начнёт возвращать `{}`, управление провалится на
следующую директиву `attackNearestBase` (`programs.ts:77`) — и ОНЭ начнёт стрелять по базе
холостыми. Запрет «ОНЭ ↛ здание» уже существует в двух местах
(`taskDefinitions.ts:FORBIDDEN_TASKS[Dew]`, `hitTest.ts:62`) — здесь он просто дотягивается до
автовыбора цели, заодно закрывая ту же дыру, которая существует и сегодня, когда врагов-роботов не
видно вовсе.

### 2. Точки применения — `client/src/engine/systems/task.ts`

Везде одинаково: `.filter((r) => worthShooting(e, r))` перед `nearest(...)`.

- `resolveAction` → `attackNearestRobot` (:248-251) и `attackNearestBase` (:252-255)
- `defendBaseOutcome` (:287-293) — внутрь уже существующего `.filter`, вторым условием
- `guardOutcome` (:498-507)
- `groupAttackOutcome` (:346-349) — обе ветки (база и робот)
- `attackAttackerOutcome` (:382-388) — ранний выход `if (!worthShooting(e, attacker)) return {}`
- `conditionHolds` → `enemyRobotWithin` (:196-201) — чтобы условие не срабатывало на цели, по
  которой действие всё равно откажется стрелять (иначе Scout/AttackBase «держат» директиву впустую)

Всё остальное **не трогаем**, и это осознанно:

- `attackTargetOutcome` (:354) — приказ игрока;
- `baseTurretTarget` (:113) — батарея базы по конфигу имеет `damage > 0`, предикат был бы мёртвым
  кодом;
- `airTarget` (:174-176) — уже требует `w.damage > 0`, ОНЭ туда не доходит;
- `disabledInRange` (:216) — обратный селектор для `finishDisabled`; его собственная проверка
  `damage <= 0` остаётся. Стоит лишь дополнить его doc-комментарий ссылкой на `worthShooting`,
  чтобы два выражения одного правила не разъехались;
- `combat.ts:currentTarget` (:124) — сюда проверку **нельзя**: она зарубила бы и приказ игрока.
  `taskSystem` идёт раньше `combatSystem` в конвейере (`gameScene.ts:98` → `:104`) и пересчитывает
  `targetId` каждый тик, так что «цель замёрзла между тиками» живёт максимум один тик.

### 3. Ручное пилотирование — не меняем

`drone.ts:fireManual` (:133-152) выбирает ближайшего врага в радиусе (включая базы) по нажатию
игрока. По решению №2 оставляем как есть. Побочный эффект известен: игрок, пилотирующий корпус с
ОНЭ, может выстрелить холостым по базе или по уже замороженному роботу. Если это захочется поправить
позже — это ровно один `.filter((e) => worthShooting(robot, e))` на строке 143.

## Тесты

`client/src/engine/systems/task.test.ts` (паттерн `visionSystem(ctx); taskSystem(ctx, DT);`
обязателен — без vision пул `knownEnemyRobots` пуст; хелперы — `makeCtx` из `testkit.ts`,
`spawnRobot`, заморозка через `foe.disabled = { left: 8 }`):

1. **ОНЭ пропускает ближнего замороженного ради дальнего живого** — два врага, ближний заморожен;
   `dew.targetId` = дальний.
2. **ОНЭ держит выстрел, когда все заморожены** — единственный враг заморожен; `dew.targetId`
   `undefined` (программа `AttackRobots`).
3. **Обычная пушка не изменилась** — тот же расклад с `WeaponType.Cannon`: цель = ближний
   замороженный (это регресс-щит для `finishDisabled`).
4. **ОНЭ не берёт базу в качестве цели** — известна вражеская база, живых роботов не видно;
   `dew.targetId` `undefined`.
5. **Ответный огонь**: `threat.attackerId` указывает на замороженного — ОНЭ не стреляет; пушка
   стреляет.
6. **Приказ игрока переживает заморозку** — `AttackTarget` с `blackboard.attackTargetId` на
   замороженном: `dew.targetId` остаётся равным ему.

Существующий тест `task.test.ts:502-513` («dew holds its shot» на Idle) должен продолжать проходить
без правок.

## Проверка

```
npm run build && npm test && npm run lint
```

`type-check` не нужен — изменения только в `client/`.

Ручная проверка в `npm run dev` (headless поведение на экране не подтвердить): собрать 1 ОНЭ + 2
обычных робота, натравить на группу из 3+ врагов и убедиться, что ОНЭ последовательно морозит
**разных** врагов, а не долбит одного, и что после заморозки всех он останавливается и ждёт вместо
стрельбы по базе.
