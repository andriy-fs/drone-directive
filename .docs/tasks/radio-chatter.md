# Радиоэфир юнитов — implementation plan

Проектное решение, согласованное до реализации. Формулировки в конце каждого раздела —
принятые решения, а не варианты.

## Context

Игре не хватает характера: происходящее на поле читается визуально и по звуку, но юниты
молчат. Хочется ленту коротких реплик поверх сцены, в стиле терминального радиообмена:

```
[01:12] ГУС.РСЗО-2: контакт в 34, 12
[01:15] КОЛ.ПУШКА-4: нарушитель разобран на запчасти
```

Основной смысл — развлекать игрока, а не информировать. Информацию уже несут HUD, звук и
сама сцена; эфир добавляет тон.

## Отвергнутая альтернатива: локальная браузерная LLM

Первым рассматривался вариант генерировать реплики на лету встроенной в браузер моделью
(Prompt API, `LanguageModel` / Gemini Nano). Отвергнут как **фундамент** фичи:

- **Охват.** Prompt API на вебе всё ещё за флагом / origin trial (стабилен только в
  расширениях Chrome). Требует desktop Chrome/Edge, ~22 ГБ свободного диска, >4 ГБ VRAM и
  разовую загрузку модели на 2–4 ГБ. Реальная доля игроков — единицы процентов.
- **Языки.** Prompt API заявлен для английского (частично es/ja). Игра локализована на
  **en / ru / uk / pl**. Nano на русском заметно слабее, на польском и украинском — плохо.
  Для проекта с четырьмя локалями это более серьёзный стоп-фактор, чем охват.
- **Латентность.** Первый токен — сотни мс, фраза целиком — 1–3 с. События в бою идут
  пачками; реплика «по событию» приезжает, когда цель уже мертва.
- **Safety.** Militaristic-формулировки («цель ликвидирована») периодически глушатся
  фильтром, ответ приходит пустой. Нужен молчаливый фолбэк в любом случае.

Также рассматривалась генерация через Workers AI на существующем релее (`server/`): даёт
100% охвата и нормальный русский, но добавляет сетевую зависимость в офлайн-игру.

**Решение:** делаем банк фраз, сгенерированный офлайн большой моделью. Работает везде и
офлайн, качество языка гарантировано, перегенерируется одной командой. Локальная LLM
позже может лишь **подмешивать** свежие строки в тот же банк — это отдельная задача.

## Принятые решения

| Вопрос | Решение |
| --- | --- |
| Локали банка | все четыре сразу (en/ru/uk/pl) |
| Координаты в репликах | сырые тайлы, `34, 12` — сектора «K-7» не вводим |
| Шрифт | системный `var(--mono)`; первый веб-шрифт в проекте не заводим |
| Позывной юнита | считается в app-слое (Map `id → номер` в директоре), движок не знает |

## Ключевое ограничение

Игра детерминированная (lockstep). **Эфир — чисто презентационный слой.** Текст не попадает
ни в ECS, ни в командную очередь, ни на провод. Лента у каждого игрока своя, и это
нормально: она отражает то, что видит именно он, сквозь его туман войны.

Отсюда — расположение по слоям:

```
engine/            эмитит события (три минимальные правки)
   ↓ EventBus
pixi/radio/        директор: фильтры, позывные, бюджет подачи   → store
   ↓ store.radio                                                    ↑
radio/             банк фраз + форматтер (общий для обеих сторон)  ─┘
   ↓
ui/hud/RadioLog    рендер: цвет, машинка, курсор, истечение
```

## Шаг 1 — движок: три минимальные правки

1. **`engine/game/events.ts`** — новое событие
   `enemySpotted: { owner; targetId; targetKind; pos }` (`owner` — сторона-наблюдатель) и
   новое опциональное поле `killerId?: string` в payload `entityDestroyed`.
2. **`engine/systems/vision.ts`**, `updateSideVision` — «обнаружения» как момента сейчас
   не существует: `intel.visibleRobotIds` пересобирается заново каждый тик. Диффим новый
   набор со старым **до** присваивания (старый Set ещё в руках) и эмитим на каждый новый
   id. Нового состояния не требуется.
3. **`engine/systems/reap.ts`** — в payload `entityDestroyed` добавить
   `killerId: e.threat?.attackerId`. Труп ещё в мире в этот момент.

Больше в движке ничего. `entitySpawned`, `baseDestroyed`, `shieldRaised`, `shieldEnded`,
`sideEliminated`, `gameOver` уже дают всё нужное.

Сознательно **не** трогаем `applyDamage` (у него нет `ctx`, и ради «попал под обстрел»
пришлось бы протаскивать шину через четырёх вызывающих). Реплики про повреждения — не в v1.

## Шаг 2 — банк фраз (`client/src/radio/`)

Новый модуль верхнего уровня: его читают и `pixi/` (директор), и `ui/` (рендер).

- `types.ts` — `RadioKey`, `UnitRef`, `RadioParams`, `PhraseBank`, плюс `SLOTS_BY_KEY`
  (какому ключу какие слоты разрешены) и `MIN_VARIANTS`.
- `bank.ts` — загрузчик, копия `i18n/dictionaries.ts`: `Record<Locale, () => Promise<…>>`
  из динамических `import()`, плюс `loaded`/`inFlight`. **Одно отличие:** синхронный
  аксессор не бросает, а возвращает `null`. Банк не нужен для первой отрисовки — грузится
  лениво на старте матча (директор дёргает `loadBank` в `sceneChanged`), до его приезда
  лента молчит.
- `locales/{en,ru,uk,pl}.ts` — контент. **В `Dict` не кладём:** `main.tsx` ждёт словарь до
  первого рендера, банк там задержал бы paint.
- `format.ts` — подстановка слотов `{unit}`, `{x}`, `{y}`, сборка позывного и `mm:ss`.

**Позывные — своя таблица `units` внутри банка, а не `chassis`/`weapons` из `Dict`.**
Изначально планировали переиспользовать словарь, но грамматика этого не выдерживает:
`chassis.tracks` = «Гусеницы», `weapons.cannon` = «Пушка», и склеенное «Гусеницы Пушка-4»
читается как ошибка. Вместо этого банк несёт `Record<ChassisType, Record<WeaponType,
string>>` — 24 коротких военных сокращения на локаль («ГУС.РСЗО», «TRK.MLRS»), что и
короче, и грамматически корректно, и соответствует терминальной эстетике ленты.

**Ключи v1:** `spotted`, `spottedBase`, `killed`, `killedBase`, `lost`, `baseLost`,
`produced`, `shieldUp`, `shieldDown`, `shieldShattered`, `enemyEliminated`, `victory`,
`defeat`.

**Объём (факт).** 12–30 вариантов на ключ, по частоте события: `spotted` — 30,
`killed` — 28, `lost`/`produced` — 24, терминальные (`victory`, `defeat`,
`enemyEliminated`, `shield*`) — 12–14, поскольку случаются раз за матч. Итого ~230 строк
на локаль; собранный чанк — **3.2 КБ gzip** на локаль, на порядок меньше первоначальной
оценки. Внутри массива намеренно смешиваются регистры — сухой уставной, усталый,
язвительный, слегка абсурдный. Случайная выборка тогда сама даёт разнообразие, и
отдельная ось «настроение» не нужна.

**Генерация и проверка.** Контент пишется большой моделью в сессии, а не скриптом с
API-ключом в рантайме. Валидатором сделан **vitest-тест `bank.test.ts`, а не hand-run
`.mjs`-скрипт**, как планировалось изначально: скрипту пришлось бы парсить TypeScript
без TS-рантайма, а обоснование ручных скриптов в этом репозитории (внешние бинарники
вроде ffmpeg, входные данные меняются пару раз в год) здесь не работает. Тест проверяет
то же самое — паритет ключей между локалями, полноту таблицы шасси×оружие, белый список
слотов, минимальные счётчики, дубли, длину строки ≤ 70 символов — и гоняется на каждом
`npm test`, а не когда о нём вспомнят.

**Локале-реактивность.** В стор кладётся **не текст**, а `key` + `seed` (случайное целое).
Рендер берёт `bank[key][seed % bank[key].length]`. Тогда смена языка посреди матча
перерисовывает уже висящие строки, а не оставляет их на старом языке; и seed не зависит от
того, что в разных локалях разное число вариантов.

## Шаг 3 — директор (`client/src/pixi/radio/radioDirector.ts`)

Разделён на два файла — по образцу `selectionAudio.ts` / `selectionSound.ts`, где адаптер
и чистая логика лежат раздельно и тестируется вторая:

- **`radioBudget.ts`** — чистая логика подачи: кулдауны, очередь, приоритеты, дедуп. Ни
  мира, ни стора, ни часов — время передаётся параметром, поэтому весь тюнинг проверяется
  тестом на ручных часах (`radioBudget.test.ts`).
- **`radioDirector.ts`** — адаптер шины: фильтры, позывные, выбор говорящего, запись в
  стор. `createRadioDirector(deps)` берёт всё внешнее инъекцией, `attachRadio(...)` —
  тонкая привязка к настоящему стору и `performance.now()`. Подключается в `GameApp`
  рядом с `attachSelectionAudio`, `destroy()` в его `destroy()`.

Обязанности директора:

- **Фильтры.** Только своя сторона. Отдельный гейт нужен ровно в одном месте — у
  `killedBase`: база не несёт `threat`, значит `killerId` для неё не приходит и ничто не
  связывает событие с нами. Там переиспользуется `GameApp.hearsBase(owner, baseId)`, тот
  же, что уже гейтит звуки купола. Остальным гейт не нужен: `enemySpotted` по определению
  означает «мы это только что увидели», а `killed` пропускается только когда убийца наш.
- **Позывные.** `Map<id, UnitRef>` — при первом упоминании юнит получает следующий номер
  по шасси; имя переживает смерть юнита, иначе `lost` не смог бы назвать погибшего.
  Очищается на `sceneChanged`.
- **Говорящий.** У `enemySpotted` автора нет — берём ближайшего своего живого робота к
  `pos` (догадка, но всегда правдоподобная: что-то наше точно в радиусе обзора, иначе
  события бы не было). У `killed` автор — `killerId`. У `lost`, `baseLost`, `killedBase`,
  купола и концовок — безличный «ШТАБ».
- **Пропускаем намеренно:** дроны (и сбитые, и обнаруженные) — у наблюдателя уже есть
  тост и передача камеры, третий канал про то же был бы шумом; и `sideEliminated` про
  себя — про это скажет `gameOver`.
- **Тон.** `alert: boolean` из таблицы в конфиге — свои потери, база, купол, поражение.
- **Заполнение очереди** — на шине, **опустошение** — в `GameApp.snapshotAfterTick()`,
  единственном хуке, общем для соло- и онлайн-пути. Побочный эффект приятный: на паузе
  мир стоит и эфир молчит.

**Бюджет подачи** — числа живут в `client/src/config/radio.ts` (dependency-free, по
конвенции `config/`), потому что это предмет тюнинга, а не логики:

| Правило | Старт |
| --- | --- |
| Глобальный минимальный интервал между строками | 2500 мс |
| Кулдаун на категорию | 5–10 с |
| Кулдаун на один юнит («не монолог») | 15 с |
| Очередь ожидающих | глубина 3, вытесняется старейшая низкоприоритетная |
| Максимум строк в ленте | 6 |
| Время жизни строки | 12 с |

**Приоритеты.** Высокий (`baseLost`, `enemyEliminated`, `victory`, `defeat`, `shield*`)
вытесняет очередь и игнорирует кулдаун категории. Средний (`killed`, `lost`, `killedBase`).
Низкий (`spotted`, `produced`) — первым отбрасывается в бою. Без этого `entityDestroyed` в
замесе летит по 5–10 раз в секунду и лента превращается в мусоропровод.

**Дедуп.** Одинаковые `(key, unitId)`, ещё не сказанные, схлопываются в одну строку.

**Кулдаун стартует в момент произнесения, а не предложения** — иначе строка, полежавшая в
очереди, заглушила бы собственную категорию ещё до выхода в эфир. На это есть тест.

## Шаг 4 — стор

По образцу chat-слайса, единственного поля без снапшота за спиной:

- `types.ts`: `RadioLine { id; key; seed; params; alert; at; elapsedMs }`, поле
  `radio: RadioLine[]`. `at` — `performance.now()` для истечения, `elapsedMs` — от старта
  матча, для префикса `[mm:ss]`.
- `gameStore.ts`: `pushRadioLine` (иммутабельный spread + обрезка), `pruneRadio(now)`
  (возвращает `{}` при отсутствии изменений — как chat-экшены), `clearRadio()`.
- `initialState.ts`, `selectors.ts` (`selectRadio`).

## Шаг 5 — рендер (`client/src/ui/hud/RadioLog.tsx`)

Третий ребёнок `.viewport` в `App.tsx`, рядом с `DroneReadyToast`. Правый верх свободен:
сайдбар слева, тост сверху по центру, чат справа снизу.

- `position: absolute; top/right: 16px; pointer-events: none; user-select: none;`
  ширина `min(360px, 42vw)`, выравнивание по правому краю, `z-index: 5` — ниже чата.
- **Фона нет** — текст прямо поверх сцены. Тёмно-зелёный `#006400` на светлой карте
  нечитаем, поэтому цвет `#00d45a`, а контраст даёт **тёмный ореол**, а не свечение того
  же цвета: два чёрных прохода в `text-shadow` плюс один слабый зелёный на «ламповость».
  Терминальность сохраняется, читаемость на песке и на воде — тоже. Все четыре цвета —
  CSS-переменные на `.radio-log`, так что тюнинг палитры это четыре строки.
  `alert` — `#ff5252` с тем же ореолом.
- Формат: `[MM:SS] ГУС.РСЗО-2: контакт в 34, 12`. Время — от старта матча.
- Сверху вниз, новое снизу; старые гаснут ступенями через `:nth-last-child` и удаляются
  `pruneRadio`.
- **Печатная машинка** — только для самой новой строки (остальные дописаны): один интервал
  ~55 мс/символ с потолком общей длительности ~2.2 с. Один таймер на компонент. Прогресс
  хранится как `{ id, n }` и сбрасывается тем, что `id` перестаёт совпадать, — иначе
  пришлось бы писать состояние прямо в теле эффекта, что запрещает
  `react-hooks/set-state-in-effect`.
- **Курсор** `▋` после последней строки, мигание ~1.4 с через `@keyframes`.
- **Один интервал 1 Гц** дёргает `pruneRadio(performance.now())` — истечение живёт в
  компоненте, а не в сторе (прецедент: `DroneReadyToast`, где видимость выводится, а не
  пишется). `pruneRadio` возвращает `{}`, если ничего не устарело: иначе новый массив
  раз в секунду перезапускал бы печатную машинку.
- `role="log" aria-live="off"` — скринридер, зачитывающий каждую шутку поверх живого боя,
  сделал бы игру неиграбельной; лента остаётся в дереве доступности, но молчит сама.
- `@media (prefers-reduced-motion: reduce)` отключает машинку (проверка в компоненте) и
  мигание с появлением строк (в CSS).

## Проверка

1. `npm run build`, `npm test`, `npm run lint` — чисто. `type-check` не нужен: правки
   только в `client/`.
2. `npm run dev`: реплики на обнаружении, убийстве, потере, постройке, куполе и в концовке;
   в замесе лента не захлёбывается; не рассказывает про чужую войну в тумане; клики
   проходят сквозь неё на канвас.
3. Смена языка посреди матча — висящие строки перерисовались.
4. Все 4 локали: переполнение в 2 строки допустимо, в 4 — нет.
5. «Уменьшить движение» в ОС — машинка и курсор замирают, текст на месте.

## Что осталось на тюнинг

Числа в `config/radio.ts` — первая прикидка, не результат игры. Крутить в первую очередь:
`minGapMs` (2500), `keyCooldownMs.spotted` (9000) и `lineTtlMs` (12000) — именно они
решают, читается лента как радиообмен или как лог. Тест `radioBudget.test.ts` берёт
значения из конфига, а не хардкодит их, поэтому правка чисел его не ломает.

## Вне объёма

- Локальная браузерная LLM как источник фраз — отдельная задача поверх готового банка.
- Генерация через Workers AI на релее.
- Фразы, зависящие от связки шасси+оружие (сейчас один слот `{unit}`), и озвучка реплик.
- Реплики про полученный урон / критическое HP (требуют шины в `applyDamage`).
- Клик по строке → подсветка сектора на карте.
