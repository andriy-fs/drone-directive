# План: не списывать бюджет за застойный шаг lockstep (фикс Причины 2)

План выполнения по диагностике `online-frame-rate-and-lockstep-stall.md`. Чинится
единственный найденный там дефект кода: цикл фиксированного шага списывает `fixedDt` из
аккумулятора безусловно, а `GameApp.stepOnline` при отсутствии ввода пира выходит, не
продвинув мир. Списанное не возвращается — когда ввод пира приходит пакетом, догонять
нечем, и мир идёт со скоростью ~60% от нормальной. Петля взаимная: свой ввод планируется
(`scheduleLocal`) только после успешного тика, так что просевший клиент задерживает пира,
а пир — его.

Цель: застойный шаг не стоит бюджета; накопленный ввод пира догоняется несколькими шагами
в одном кадре; мир возвращается к 30 тикам/с даже при 30 fps.

Вне объёма (по самой диагностике): Причина 1 (GPU/композитор — вне кода), Причина 3
(интерполяция рендера — отдельная задача после этой), Причина 4 (свойство дизайна).

## Изменения

### 1. `client/src/pixi/GameLoop.ts` — шаг с признаком «продвинулись ли»

- `UpdateFn`: `(dt: number) => void` → `(dt: number) => boolean`. `true` — шаг потреблён
  (мир продвинулся или бюджет потрачен законно), `false` — **только** застой lockstep,
  бюджет вернуть.
- Цикл:
  ```ts
  while (this.accumulator >= gameConfig.fixedDt) {
    if (!this.update(gameConfig.fixedDt)) break; // застой: бюджет не списывать
    this.accumulator -= gameConfig.fixedDt;
    this.steppedSinceResume = true;
    steps++;
  }
  ```
  `steppedSinceResume` ставится только на потреблённом шаге — семантика «фиксированный шаг
  действительно прошёл» сохраняется (застой возможен только внутри матча, а `park()`
  случается только в меню, так что ловушка из `menu-start-restart-idle-loop.md` не
  затрагивается).
- **Потолок аккумулятора** — обязательное дополнение: при `break` без вычитания
  аккумулятор копится через кадры неограниченно, и после долгого застоя один кадр
  попытался бы отсчитать сотни тиков. Ограничить при пополнении:
  `this.accumulator = Math.min(this.accumulator + frameDt, gameConfig.maxFrameDt)`.
  `maxFrameDt` (0.25 s = 7 тиков при 30 Гц) уже играет ровно эту роль для вклада одного
  кадра — переиспользуется как общий потолок, новой константы не нужно.
- `alpha`: после `break` аккумулятор может быть ≥ `fixedDt` — клампить:
  `Math.min(this.accumulator / gameConfig.fixedDt, 1)`. Потребителя у `alpha` пока нет
  (Причина 3), но отдавать в `RenderFn` значение вне [0, 1] нельзя.

### 2. `client/src/pixi/GameApp.ts` — `false` возвращает только застой

- `step(dt)` → `boolean`. Все ранние выходы, кроме застоя, возвращают `true` — они не
  застой и обязаны потреблять бюджет, иначе изменится поведение меню и старта матча:
  `startHeld` (ожидание спрайтов), `pendingOnlineStart` (первый тик сетевого матча),
  `restartRequested`/`menuRequested`, соло-ветка.
- `stepOnline(...)` → `boolean`: `false` в единственной ветке
  `!session.ready(this.netTick)` (счётчики `stallWindow`/`noteStall` там же, как сейчас),
  `true` после успешного тика.
- Ветка «сессия есть, но матч ещё не `InMatch`» (проваливается в соло-путь) не меняется.

Догон получается сам собой: при `true` цикл в `GameLoop` продолжает крутиться, `step`
снова зовёт `stepOnline` со следующим `netTick`, и накопленные тики пира съедаются в одном
кадре, пока аккумулятор не иссякнет. `scheduleLocal` при этом зовётся на каждом успешном
тике — просевший клиент быстрее восстанавливает поток своего ввода, размыкая взаимную
петлю.

Побочная смена семантики `net stall %` в HUD: раньше застой считался на каждой итерации
while (могло быть несколько за кадр), теперь — не больше одного на кадр (`break`).
Показатель остаётся «доля попыток шага, вставших в ожидание»; учесть при перемере.

### 3. `client/src/pixi/GameLoop.test.ts` — дополнить

- Существующие колбэки `update` возвращают `true` (в т.ч. инлайн-цикл в тесте «always
  consumes a one-shot request…»).
- Новые тесты:
  - застой не списывает бюджет: `update` возвращает `false` N кадров подряд — аккумулятор
    не тает, `steps` = 0, рендер каждый кадр идёт;
  - догон: после серии `false` update начинает возвращать `true` — один кадр прогоняет
    несколько шагов;
  - потолок: сколько бы ни длился застой, после восстановления кадр делает не больше
    `maxFrameDt / fixedDt` шагов;
  - `steppedSinceResume`: кадр, где каждый шаг встал, не даёт `park()` право сработать.

## Проверка

1. `npm run build`, `npm test`, `npm run lint` — чисто (база: 45 + 27 + 393 теста).
2. Онлайн вживую: `npm run dev` + `npm run dev:relay`, матч в двух браузерах с `?perf=1`:
   `net stall %` падает с ~40%; скорость мира на глаз нормальная (не «замедленная
   съёмка»); соло, старт/рестарт/выход в меню, парковка на титульном экране — без
   регрессий.
3. Перемер по методике диагностики (60×60, `npm run preview`, n=240); цифры — в
   `online-frame-rate-and-lockstep-stall.md`.

Затронутые слои — только `client/src/pixi/**`; wire-протокол, `net/` и сервер не
меняются.
